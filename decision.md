# StockWise decisions

## 2026-11-21 · Stage 1 · Repository and package

- **Decision:** Use a `stockwise` installable Python package, `pyproject.toml`, root `alembic/`, and `tests/`. **Alternatives:** single-file modules, monorepo placeholders. **Reason:** imports stay separable and later API code can consume pure modules. **Trade-off:** package install is needed before running tests.
- **Decision:** Keep Stage 1 limited to domain/data modules, migration, tests, and requested project notes. **Alternatives:** scaffold later frontend/API/compose folders. **Reason:** scope explicitly excludes them. **Trade-off:** this stage cannot yet be run as a complete app.
- **Assumption:** Python 3.12 is the target; `scipy.optimize.milp` and PostgreSQL are runtime requirements. Dependencies are declared, not vendored.

## 2026-11-21 · Stage 1 · Persistence

- **Decision:** Model `users`, `products`, `sales_weeks`, `upload_batches`, `plans`, and `plan_items` in SQLAlchemy 2.0, with Alembic revision `0001_stage1`. **Alternatives:** SQLModel, ORM-only `create_all`. **Reason:** requested stack and reproducible Postgres schema migration. **Trade-off:** migration URL must be configured for a real deployment.
- **Decision:** Use integer primary keys, seller foreign keys with cascade deletion, seller-scoped unique SKUs, and unique product/week sales. Keep costs/profits as `Numeric(12,2)` and retain immutable plan inputs as PostgreSQL JSONB. **Alternatives:** float money and generic JSON. **Reason:** avoid persisted money rounding drift and preserve reproducible plans. **Trade-off:** JSONB is Postgres-specific.
- **Decision:** Represent weeks as Monday `DATE`; record upload timestamp and associate sales rows with their upload batch. **Alternatives:** week string or batch replacement. **Reason:** ISO calendar weeks and append/history provenance. A repeated product/week is constrained unique and must be resolved by a later upload policy. **Trade-off:** the future upload endpoint must define upsert behavior.
- **Decision:** Put `stockout_flag` on each `sales_weeks` row and keep product min-order/pack-size fields. **Alternatives:** encode these in upload data. **Reason:** these are seller-maintained planning facts, not weekly sales values.

## 2026-11-21 · Stage 1 · Forecasting

- **Decision:** Implement moving average, simple exponential smoothing, and rolling one-step MAE selection with default window 3 and alpha 0.4. Ties deterministically favor exponential smoothing (lexicographic name order). With fewer than three nonblank observations return last week with `low` confidence. **Alternatives:** trend fit, random tie resolution, training a model. **Reason:** matches the specified transparent, request-time methods. **Trade-off:** small samples have weak evidence and forecasts can be fractional.
- **Decision:** Treat blank periods as omitted observations while retaining zero as a valid observation; when stockout flags are passed, clamp the forecast to at least the largest flagged sales observation. **Alternatives:** impute blank weeks as zero or treat stockout sales as exact demand. **Reason:** blank is missing and stockout sales are lower bounds. **Trade-off:** a single high censored observation can lift the forecast; no censored-demand model is inferred.
- **Decision:** Use `Forecast` as an immutable result containing float demand, method, confidence, observed history and optional MAE. **Alternatives:** return a scalar. **Reason:** callers need to display forecasting provenance.

## 2026-11-21 · Stage 1 · Optimization

- **Decision:** Use SciPy `milp` with one integer variable per product pack count, maximize profit under spend, demand, minimum, pack and optional storage bounds. Compute a separate SKU-tie-broken greedy profit-per-cost baseline. **Alternatives:** OR-Tools, custom branch-and-bound, greedy-only. **Reason:** the user specified SciPy MILP and greedy comparison. **Trade-off:** exact result depends on SciPy/HiGHS availability.
- **Decision:** Convert units into integer pack counts, floor risk-adjusted/overridden demand to whole units, default risk multiplier 1.0, and disable optional products with nonpositive unit profit. Forced include means at least one complete pack unless a larger minimum is provided; forced exclude is zero. **Alternatives:** allow partial packs or buy loss-making optional goods. **Reason:** preserve whole-unit and sensible positive-return behavior. **Trade-off:** pack flooring can leave a small demand remainder unbuyable; forced include with no positive margin is infeasible.
- **Decision:** Expose infeasible mandatory bounds as `InfeasiblePlan`, malformed inputs as `ValueError`, and solver faults as `RuntimeError`. Ties are left to deterministic solver behavior; the greedy tie break is SKU order. **Alternatives:** silently relax minima. **Reason:** constraints should not be changed without seller consent.
- **Assumption:** ROI means expected profit divided by money spent (zero if nothing is spent); storage limit counts physical units, not packs.

## 2026-11-21 · Stage 1 · Upload validation

- **Decision:** Parse CSV using the standard library and XLSX with openpyxl in read-only/data-only mode; return typed product and ISO-Monday sales rows. Accept exactly the specified wide columns and long columns (`sku,week,units_sold`); long imports require existing SKU names supplied by the caller. **Alternatives:** pandas coercion, silently ignore unknown columns/SKUs. **Reason:** strict row visibility and small focused dependencies. **Trade-off:** long imports intentionally do not create/update product metadata.
- **Decision:** Enforce 10 MiB and 10,000 data-row limits; blank wide cells are omitted, zero is kept, duplicate SKU/week keys and malformed rows are errors. **Alternatives:** partial successful import. **Reason:** never silently lose or accept bad rows. **Trade-off:** a single bad row rejects the batch with all collected validation errors.

## 2026-11-21 · Stage 1.5 · Domain corrections

- **Supersedes the Stage 1 MOQ decision:** Treat MOQ as an optional activation threshold. The solver may buy zero, or a whole-pack quantity rounded up to meet MOQ. A forced inclusion activates that binary; if the adjusted cap cannot reach its threshold, return an explicit infeasibility. **Alternatives:** force every MOQ product into every plan; allow partial pack fulfillment. **Reason:** an MOQ is a vendor condition, not a mandatory purchase. **Trade-off:** the ILP becomes a MILP with one activation binary for MOQ/forced products.
- **Supersedes the Stage 1 stockout forecast floor:** For each flagged observation, adjust it to `max(observed, mean(unflagged history))` before forecasting. If all weeks are flagged, retain the observations and label confidence low. Keep only the required recent flagged-week lower bound on the final forecast; do not clamp every future forecast to the maximum historical stockout. **Alternatives:** treat every stockout value as exact demand or permanently floor forecasts at the largest flagged sale. **Reason:** stockout data is censored while an old stockout should not become a permanent demand floor. **Trade-off:** the unflagged mean is only a simple baseline and cannot recover lost sales or seasonality.
- **Decision:** Add `risk_mode` (`safe`, `balanced`, `aggressive`) alongside the numeric `demand_scale`; the factors multiply. Retain explicit numeric scaling for callers that need another scenario. **Alternatives:** remove numeric scaling or map names in the web layer only. **Reason:** the pure optimizer must support named seller modes and composable inputs. **Trade-off:** callers can create an unusually high combined cap, which remains bounded only by forecast and seller constraints.
- **Decision:** Make every CSV/XLSX validation issue include `row`, `column`, `value`, and `message`; aggregate cell issues across rows and return nonfatal warnings for blank weeks where other weeks have data. Accept only properly grouped thousands commas and an optional leading `₹` in monetary fields; accept thousands grouping in unit counts. **Alternatives:** permissive comma removal, first-error-only validation. **Reason:** formatted Indian-market inputs should work without guessing or hiding malformed data. **Trade-off:** formatted comma-containing CSV cells must be quoted as normal CSV syntax requires.
- **Verification:** Stage 1.5 forecast/optimizer/import suite ran with `60 passed`, including 300 seeded random ILP comparisons against enumeration. The sample seed makes the property-style cases repeatable rather than nondeterministic.

## 2026-11-21 · Stage 2 · FastAPI backend

- **Decision:** Use synchronous FastAPI routes, SQLAlchemy 2.x `Session`, and psycopg. **Alternatives:** async routes/asyncpg. **Reason:** persistence and SciPy solve calls are synchronous. **Trade-off:** each solve occupies a request worker while it runs.
- **Decision:** Use Argon2 password hashes, HS256 JWT cookies with a 12-hour lifetime, `HttpOnly` and `SameSite=Lax`; set `Secure` in production. Bootstrap a double-submit CSRF cookie via `GET /auth/csrf` and require its matching `X-CSRF-Token` header for every state-changing endpoint. Production requires `JWT_SECRET`; local development uses a random per-process secret. **Alternatives:** browser-storage bearer tokens, bcrypt, cookie-only CSRF. **Reason:** match the requested cookie auth and provide an explicit CSRF defense without checking real secrets into Git. **Trade-off:** local sessions expire on restart; production needs a stable secret.
- **Decision:** Use Pydantic v2 schemas with extra fields forbidden, Argon2, PyJWT, email-validator, and python-multipart. Normalize emails to lowercase. **Alternatives:** hand-written JSON validation, another password/JWT library. **Reason:** typed validation for the requested REST stack and multipart uploads. **Trade-off:** formatted monetary values are normalized by the import parser, while JSON APIs accept decimal values.
- **Decision:** Keep REST handlers in `stockwise/api.py` and keep forecasts/optimization in their pure modules. All product, history, upload, plan, and settings lookups are scoped to the authenticated `owner_id`; foreign IDs return 404. Use a consistent `{error:{code,message,details}}` response. **Alternatives:** expose domain/web dependencies in forecast modules or return 403 for foreign IDs. **Reason:** keep algorithms reusable and avoid disclosing another seller's identifiers.
- **Decision:** Add Alembic revision `0002_api` for product forecast overrides/notes, a stored plan-result snapshot, a nonnegative override constraint, and one seller currency setting defaulting to INR. Keep `0001_stage1` untouched. **Alternatives:** add API-only columns to `0001`, attach currency to each plan, reconstruct saved plans from mutable product rows. **Reason:** preserve migration history, keep account settings stable, and reopen the original plan. **Trade-off:** JSONB plan snapshots and settings migration are PostgreSQL-specific, matching the configured database.
- **Decision:** Preview parses and validates without writes; commit writes the batch, product upserts, and sales changes in one transaction. A newer upload overwrites a repeated product/week value and records the newer batch ID. Long-format rows must reference the current seller's product. **Alternatives:** reject repeated weeks, partial row commits, global SKU lookup. **Reason:** follow the latest-upload-wins policy without weakening all-or-nothing validation. **Trade-off:** old sale values are replaced; the latest row retains batch provenance but no revision log of prior quantities exists.
- **Decision:** Save budget, risk, storage, flags, forecast settings, per-product economics/constraints, forecasts/history, optimizer result, totals, and greedy quantities with each plan. Export stored results as CSV. **Reason:** saved plans should not change when product settings or sales later change.
- **Decision:** Configure runtime using `DATABASE_URL`, `JWT_SECRET`, `FRONTEND_ORIGIN`, and `ENVIRONMENT`; restrict credentialed CORS to the configured single origin. Add `.env.example` containing only a replaceable secret placeholder. Public read-only routes are the CSRF bootstrap and CSV template downloads.
- **Verification:** disposable PostgreSQL 17.6, migrations through `0002_api`, full pytest suite `132 passed, 1 warning in 13.38s`, and Alembic `check` output `No new upgrade operations detected.` The warning is Starlette's TestClient/httpx deprecation notice; it did not fail tests.

## 2026-11-21 · Stage 2 bug fix · Fractional demand

- **Decision:** Accept any finite nonnegative forecast or forecast override in `solve_plan`, multiply by the numeric and named risk scales, then floor the adjusted demand to whole units before pack bounds are built. Keep the displayed/statistical forecast fractional. **Alternatives:** reject fractional values, round them before scaling, or round the final cap to nearest. **Reason:** statistical forecasts and seller overrides are naturally fractional, while order quantities must remain whole; flooring after risk adjustment is conservative and matches the existing unit-cap behavior. **Trade-off:** a fractional remainder cannot be ordered, and pack sizes may reduce the cap further.
- **Decision:** The generic API 500 handler logs the request method/path and the actual exception traceback with `logger.error(..., exc_info=...)`, while returning the same generic error body. **Alternatives:** return exception text to clients or log only a message. **Reason:** retain useful server diagnostics without disclosing internals over the API. **Trade-off:** server logs now contain exception details and require normal access controls.
- **Decision:** Extend the seeded brute-force comparison with fractional product demands and overrides, and unit-test the generic handler with a logger spy that inspects the traceback tuple. **Reason:** validate both optimization correctness and traceback handoff without relying on thread-specific pytest log capture.
- **Verification:** with PostgreSQL 17.6, full pytest ran as `140 passed, 1 warning in 13.01s`; Alembic `check` reported `No new upgrade operations detected.` The single warning remains Starlette's TestClient/httpx deprecation notice.
